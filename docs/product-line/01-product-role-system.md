# 产品角色体系事实基线

- 状态：`active-design-baseline`
- 日期：2026-07-31
- 范围：下一产品线角色、责任、权限边界与迁移约束
- 非完成声明：本文是基于当前代码的产品决策，不代表对应界面或权限迁移已经发布

## 1. 当前代码事实

1. 人类成员角色由 `backend/app/models/user.py` 定义为 `platform_admin`、`org_admin`、`agent_admin`、`member`。`Identity` 表达跨租户自然人，`User` 表达该自然人在一个租户内的成员身份。
2. 私人助手没有独立 Agent 类型。它由 `backend/app/api/onboarding.py` 以普通 `Agent` 创建，通过 `role_description="Private Assistant"`、`access_mode="private"` 和当前用户的 `manage` 权限表达，并由 `UserTenantOnboarding.personal_assistant_agent_id` 建立 `(tenant, user)` 关联。
3. 注册页允许用户设置私人助手名称、性格、办事风格和边界，但把它称为“第一位员工”；`Layout.tsx` 又把它放进普通“智能体”列表。
4. 长期 Agent 员工由 `Agent`、`AgentTemplate`、`AgentPermission`、Skill、Tool、Trigger、Channel、Workspace 等对象共同表达。Skill 只提供做事方法，Tool 才是可执行能力。
5. 当前没有独立的“临时专家”持久模型。一次性专业工作要么被迫交给私人助手，要么要求用户先创建长期 Agent，要么直接使用某个现有 Agent。
6. Group 是租户内长期群聊对象，成员是 `Participant`，群成员角色只有 `manager` 和 `member`；Group 不是人类组织架构，也不是一个新的 Agent。

## 2. 已确认的目标角色

| 产品角色 | 身份寿命 | 主要责任 | 可以做 | 不可以成为 |
|---|---|---|---|---|
| 普通成员 | 一个租户成员周期 | 提出任务、使用获授权员工、参与协作、验收自己的工作 | 使用工作台、自己的助理、可见 Agent、Group、产物和经验 | Provider/模型管理员；默认访问他人私人内容 |
| 公司管理员 | 一个租户成员周期 | 公司成员、数字员工、模板、权限、套餐和企业政策 | 管理租户资源、分配 Agent 管理权、发布公司模板、查看合规审计 | SaaS Provider 全局运维；默认读取成员私人助手内容 |
| Agent 管理员 | 授权周期 | 管理被明确授权的数字员工 | 配置角色、Skill、Tool、Trigger、Channel、可见性和升级路径 | 等同公司管理员；管理未授权 Agent |
| 平台管理员 | 平台运营周期 | Provider 账号池、路由、套餐、Credits、健康、审计、发布身份 | 运维 SaaS 控制面和全局政策 | 代替租户做业务审批；日常进入租户私人工作 |
| 私人助手 | 每个 `(tenant, user)` 一个长期槽位 | 私人协调、跟进、备忘、草拟、轻量计划、帮助派发工作 | 记住个人偏好；找到合适员工/专家；在授权范围内发起任务 | 公司共享员工；全能专家；绕过审批；占用数字员工席位 |
| Agent 员工 | 长期 | 承担明确、可命名、可持续的业务职责 | 持久记忆、定时/事件触发、渠道、KPI、明确技能与工具 | 一次性临时工具；没有责任边界的通用聊天机器人 |
| 临时专家 | 单个 Task/Run 生命周期 | 完成一次专业任务 | 使用平台选择的角色配置和最小能力集，产物归入本次任务 | 出现在长期员工花名册；持久吸收跨任务私人记忆；拥有长期 Trigger/Channel |
| Group | 长期协作空间 | 让多个人与 Agent 围绕同一上下文协作、交接和审批 | 维护成员、会话、共享 Workspace、显式 @ 与协作状态 | 责任人本身；公司通讯录；隐藏的 Agent 编排黑盒 |

## 3. 私人助手的产品定义

### 3.1 固定角色，名称可选

- 产品角色固定为 `personal_assistant`，注册时不要求用户设计职业或选择 Skills。
- 主导航固定显示“我的助理”，用户自定义名称作为二级身份，例如“我的助理 · 小岚”。
- 用户可以在注册时命名，也可以跳过；跳过必须创建安全默认助手，不能把“跳过”实现为再次调用同一个创建动作却不解释结果。
- 后续可修改称呼、响应风格、主动程度、时区/工作时间和边界，但不能把私人助手原地改造成共享数字员工。

### 3.2 权限与计费

- 私人助手默认 `private`，仅用户本人可使用和管理；公司管理员只能管理政策与审计，不默认读取会话和 Workspace。
- 它不计入数字员工席位，但文字、媒体、外部 Tool 和存储仍正常受套餐、Credits、授权和审计约束。
- 它不自动继承公司全部 Tools，也不因以后注册新 Skill 自动获得执行权限。
- 外部发送、发布、付费生成、删除和企业系统写入仍需对应授权与审批。

### 3.3 委派边界

- 私人协调、草拟、提醒：由私人助手直接处理。
- 一次性专业结果：由私人助手或工作台创建 Task，并路由给临时专家。
- 长期职责：建议用户招聘/创建数字员工，并由该员工持续负责。
- 多方可见协作：进入 Group；私人助手不能把自己的私有记忆静默复制到 Group。

## 4. Agent 员工与临时专家的判定

只有满足至少一项条件时，才建议创建长期 Agent 员工：

- 需要跨任务持久专业记忆；
- 需要定时、Webhook 或事件触发；
- 需要飞书、企微、钉钉等长期渠道身份；
- 需要被公司成员反复发现和使用；
- 需要明确负责人、KPI、升级和交接关系。

其他一次性调研、单次 PPT、一次广告视频、一次数据分析默认使用临时专家。临时专家由平台内部选择，不要求用户先“招聘”。

## 6. 当前主要问题

1. **身份概念冲突**：注册称私人助手为“第一位员工”，导航把它与公司 Agent 混排，用户无法理解谁是私人关系、谁是公司资源。
2. **一次性任务被员工化**：没有临时专家对象，迫使用户先理解 Agent 和 Skill，再完成一次任务。
3. **权限角色与产品称谓不一致**：`agent_admin` 是真实用户角色，但产品中缺乏清晰的“管理哪些员工”说明。
4. **Group 容易被误解为编排器**：当前 Group 的真实权威是成员和会话，不应宣传成自动分工的万能团队。
5. **私人助手席位语义未固化**：当前创建会执行普通 Agent 配额检查，和“不占员工席位”的目标存在实现差距。

## 7. 无破坏迁移规则

- 保留所有现有 Agent ID、会话、Workspace、权限和深链；只新增角色标签和入口分组。
- 通过 `UserTenantOnboarding.personal_assistant_agent_id` 识别现有私人助手，不按名称猜测。
- 迁移前检测一名用户是否有多个候选私人助手；冲突进入管理员修复队列，不自动合并内容。
- 临时专家第一阶段作为 Task/Run 的执行策略和快照实现，不先新增可见员工记录。
- 现有 `agent_admin` 权限不扩大；新增界面必须基于服务端 `manage` 关系判定。
- 私人助手的员工席位豁免需要产品/财务批准和服务端配额改造后才生效。

## 8. 完成标准

- 注册、导航、Agent 列表、Group 成员和企业管理对上述角色使用一致术语。
- 普通成员无需理解 Skill、Tool、Provider 或模型即可完成首次任务。
- 私人助手与数字员工在界面、权限、配额、发现和协作行为上均可区分。
- 一次性任务无需创建长期员工，并且其执行者、授权、Run 和 Artifact 仍可审计。
