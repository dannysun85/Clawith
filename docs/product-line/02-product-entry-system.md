## 2. 目标入口定义

### 2.1 工作台：默认任务入口

名称确定为 `工作台`，不叫“助手”或“超级助手”。它是任务入口与工作索引，不是一个拟人角色。

#### 2.1.1 产品定位与用户目标

工作台是**当前用户的统一任务控制面**。用户在这里表达要达成的业务结果，系统把意图转成稳定的
`Task/Run/Deliverable`，并持续告诉用户“现在到哪一步、谁在负责、下一步需要谁做什么”。它既接住用户主动发起的
任务，也汇总系统在授权范围内创建、且当前用户有责任或可见性的任务。

工作台不是聊天收件箱、Agent 名册、Group 会话、文件管理器或新的 Runtime。它只投影现有业务对象，并深链回真实
执行现场。

#### 2.1.2 允许进入工作台的触发来源

| 来源 | 如何进入工作台 | 产品约束 |
|---|---|---|
| 用户在工作台发起 | 输入自然语言并按需附文件、图片或语音 | 默认自动推荐执行者；确认工作说明后才创建正式执行 |
| 用户在 Agent 对话中明确发起 | Agent 对话把已确认工作登记为 Task | 普通对话不自动升级为任务；必须有明确“创建任务/开始执行”动作 |
| 用户在协作群组中明确创建或转换 | 从群组消息、会话或任务面板创建关联 Task | 原消息保留；转换后展示稳定 Task ID、责任主体和关联会话 |
| Trigger、Channel、API、定时或策略 | 预先授权的自动化创建 Task/Run | 必须记录触发来源、策略和幂等键；风险、费用或外部动作仍走审批 |
| 领域对象要求用户行动 | Review、Approval、失败恢复或澄清形成 inbox 项 | Work 只提供权威对象的行动入口，不复制审批或评审状态 |

系统可以自动创建已获授权的任务，但不能因此静默创建 Group、添加成员、改变可见范围或绕过费用/外部动作审批。

#### 2.1.3 支持的工作类型

| 工作类型 | 工作台如何处理 | 是否需要协作群组 |
|---|---|---|
| 单一任务 | 一个主要责任主体完成一次明确结果 | 默认不需要 |
| 复杂单责任任务 | 同一责任主体拆解步骤、多次尝试、返工和版本 | 默认不需要；全部 attempt/revision 归入同一任务详情 |
| 系统跨模块编排 | Task 跨 Agent、Workspace、Artifact、Review、Approval 和 Delivery | 不等于多人协作；仍可只在工作台管理 |
| 多方可见协作 | 多个人或 Agent 需要讨论、分工、交接、共同评审或批准 | 需要关联协作群组；工作台继续展示摘要和当前行动 |
| 持续性工作 | 数字员工或 Trigger 周期执行，按策略产生独立运行或任务 | 有固定协作班组时可关联群组，否则不强制 |

“复杂”与“跨模块”都不自动等于 Group。是否进入协作群组只取决于过程是否需要多个参与方共享上下文并显式互动。

#### 2.1.4 页面内容与信息层级

工作台保持一个入口，内部包含以下区域：

1. **任务发起区**：目标、附件和关键约束；普通用户不先选 Provider、model、Skill 或 Tool。
2. **系统建议与确认**：显示推荐责任主体、原因、能力/权限/费用/审批预检以及可用替代项；手工选择执行者放在高级设置。
3. **待我处理**：只汇总有权威责任事实的澄清、Review、Approval、失败恢复或交付确认。
4. **进行中**：当前用户创建、被分配或有明确管理责任的活跃任务。
5. **最近完成**：近期完成、已交付或已终止的可见任务，可继续查看、复用或沉淀经验。
6. **任务详情**：工作说明、来源、主要责任主体、协作群组、完整 attempts/runs、时间线、Artifact 版本、评审、审批、交付和下一步动作。

任务卡片至少展示：任务标题、触发来源、主要责任主体、当前阶段、最新进展、下一步行动、优先级/期限，以及 Agent、Group、Artifact、Review、Approval 或 Delivery 的真实深链。

#### 2.1.5 状态与行动规则

工作台可使用 `待确认 / 进行中 / 待我处理 / 可交付 / 已完成 / 异常或已取消` 作为面向用户的阶段投影，但不得新增第二套
状态机。阶段必须由 `Task`、`AgentRun`、`Artifact`、`QualityReview`、Runtime `ApprovalRequest`、
`DeliverableApprovalReceipt` 和 Delivery 事实计算。

- 没有明确 `awaiting_actor`、reviewer、approver 或 creator 恢复责任时，不生成“待我处理”。
- 一个任务可有多次 Run/attempt 和多个 Artifact revision；最新一次成功不能掩盖历史失败，部分成功也不能显示为整体完成。
- Runtime 执行状态与结果通知投递状态是两个独立事实。`run_failed` 后出现 `delivery_succeeded` 只表示失败通知已送达，绝不能把 Run、Task 或 Group 卡片显示为执行成功；界面应并列显示“执行失败 · 结果通知已送达”。
- 所有操作调用原领域 API；工作台不另建 approve、review、deliver 或 cancel 真相。
- 权限、成员身份或对象授权撤销后，已打开的页面、缓存和旧 action URL 都必须 fail closed。

#### 2.1.6 核心交互流程

```text
表达结果与约束
  -> 系统澄清必要信息
  -> 推荐主要责任主体并给出原因
  -> 能力/权限/费用/审批预检
  -> 用户确认工作说明（或授权策略自动确认）
  -> 幂等创建 Task 与首个 Run
  -> 在 Agent 或协作群组现场执行
  -> 工作台持续投影进度和待办
  -> Review / Approval / Delivery
  -> 完成、复用或沉淀为经验
```

普通用户的首条路径是“说清要什么”，而不是“先配置怎么做”。管理员也使用相同的个人任务面，不因管理角色默认看见其他员工的私人任务。

工作台负责：

- 接收自然语言、文件、图片和语音输入；
- 提供按业务结果组织的快捷入口；
- 识别任务类型并补齐关键约束；
- 提议由私人助手、临时专家、数字员工或 Group 处理；
- 展示能力、费用和审批预检摘要；
- 聚合 `等待我处理`、`进行中`、`最近完成` 和常用工作；
- 深链回真实 Agent/Group 会话、Deliverable 详情和 Workspace Artifact。

工作台不负责：

- 自己成为一个 Agent；
- 复制 Task/Run/Deliverable 状态；
- 暴露 Provider、模型、Skill 或 Tool 选择；
- 新建第二套调度器或文件系统。

### 2.2 我的助理：默认私人协调关系

- 导航固定显示 `我的助理`，自定义名称作为副标题。
- 用于备忘、跟进、草拟、轻量计划和任务派发。
- 它可以帮用户找工作和派发工作，但正式任务仍落到 Task/Run/Deliverable。

### 2.3 数字员工：长期执行角色

- 展示公司/私有/自定义的长期 Agent 员工。
- 用户在需要长期责任、触发器、渠道或持续记忆时才进入招聘/创建流程。
- 员工卡展示业务职责和可完成的工作，不把原始 Skill 列表当商品描述。
- `/employees` 是唯一公司级员工索引：桌面默认协作网络，移动默认员工名册；两种视图必须使用同一份按当前用户裁剪的员工投影。
- 左侧导航只显示一个带数量的 `数字员工` 入口，不复制完整列表、搜索、收藏或添加控件。
- 添加从页头/空状态进入员工市场，模板招聘优先、自定义创建为高级入口；创建前确认职责、交付边界与可见范围，不要求普通用户选择 Provider、模型、Skill 或 Tool。
- `仅创建` 回到名册并高亮新员工；`创建并开始对话` 进入既有 Agent 消息界面；设置仅对有管理权的用户显示。

### 2.4 协作群组：多人和 Agent 的可见协作现场

#### 2.4.1 产品定位与边界

协作群组负责多个人和 Agent 围绕共同工作共享上下文、讨论、分工、交接、评审和审批。它是长期或阶段性的协作空间，
不是组织架构图、Agent 员工目录、隐藏调度器，也不是工作台的另一种列表视图。

群组中的普通消息首先是沟通记录，不自动变成任务。只有用户明确“创建任务/转换为任务”，或已有授权的自动化明确关联稳定
Task 时，才进入正式任务生命周期。每项正式工作必须有一个主要责任主体和稳定 `Task/Run ID`；参与者多不等于责任主体可以为空。

#### 2.4.2 适用工作

- 多角色共同规划，需要公开记录方案和决策；
- 多个人或 Agent 分工执行，需要明确 owner、handoff 和依赖；
- Agent 产出后由人类评审、修改、批准或交付；
- 跨团队项目、事件处置、周期运营或需要持续共享 Workspace 的工作；
- 用户需要在同一会话中看到多方进度、Artifact 和审批结果。

只有一个主要执行者、其余能力由系统内部调用的任务，不应为了“看起来复杂”而自动创建协作群组。

#### 2.4.3 触发方式

| 触发者 | 允许动作 | 必须满足 |
|---|---|---|
| 用户 | 新建 Group、邀请可见成员、创建会话、在群组中创建正式任务 | 创建者有相应成员/对象权限；任务确认后产生稳定 ID |
| 用户 | 把一条已持久化且当前可见的消息转换为任务 | 先进入确认面板；明确选择主要责任主体；保留来源消息和 correlation |
| 工作台 | 将已确认的多方任务关联到用户显式选择的既有 Group | 不静默新建 Group，不静默选择或添加成员 |
| 系统自动化 | 向已有且预授权的 Group 发布进度、创建/关联任务 | 记录 trigger、policy、actor 和幂等键；遵守当前成员可见性 |

系统不得仅根据文本推断就创建群组、加入参与者、扩大 Workspace 可见范围或代替人类执行高风险批准。

#### 2.4.4 页面内容与任务上下文

协作群组页面维持现有群组树和消息体验，并把正式任务上下文做成清楚的协作面：

1. **群组与会话导航**：群组树、会话、未读和公告。
2. **消息与活动流**：人和 Agent 消息、@、系统事件、交接和任务状态更新。
3. **成员与责任**：成员列表、群组管理员；正式任务另显示唯一主要责任主体、参与者和当前接手人。
4. **关联任务**：展示 Task ID、工作说明、阶段、下一步行动、Runs、Artifact、Review、Approval 和 Delivery 深链。
5. **Group Workspace**：保存该群组共享的文件、草稿和中间产物；不复制 Agent 私有 Workspace，也不充当正式交付真相。

当前版本一个正式 Task 只设置一个主要协作 Group 上下文，一个 Group 可以承载多个 Task。需要多个群组共同完成时，先由一个 Task/owner 负责跨群组协调，不在本轮引入多主群组状态同步。

#### 2.4.5 权限和状态规则

- 非成员不能读取群组、会话、消息、文件、Run 或关联任务上下文；直接对象访问也必须由服务端拒绝。
- 群组管理员负责群组设置和成员管理；这不自动授予其对关联任务、Artifact、Review、Approval 或 Delivery 的操作权。
- 任务动作继续按 Task/Agent/Review/Approval 对象权限判断；UI 隐藏不能代替服务端鉴权。
- Group 不维护独立的“任务完成状态”；消息中的状态卡和活动事件来自真实 Task/Run/Deliverable 对象。
- Agent 或成员失败、离线、被移除、权限撤销时，必须保留可审计事件，并明确阻塞、重分配或取消选项，不能假装完成。

#### 2.4.6 核心协作流程

```text
用户或已授权系统确定需要可见多方协作
  -> 选择已有 Group（或由用户显式创建并配置成员）
  -> 明确工作说明与唯一主要责任主体
  -> 幂等创建/关联 Task、Run、session 和 correlation
  -> 讨论、分工、执行、@、文件与 handoff
  -> Artifact 进入 Review / Approval
  -> Delivery 或阻塞/恢复
  -> 工作台同步投影任务摘要和当前用户行动
```

#### 2.4.7 与工作台的职责关系

| 问题 | 工作台负责 | 协作群组负责 |
|---|---|---|
| 用户从哪里看到所有自己的工作 | 统一任务索引、筛选和待办 | 不负责跨任务总览 |
| 用户从哪里发起任务 | 默认入口，也可承接其他入口 | 可在具体共享上下文中显式发起 |
| 多方在哪里讨论和交接 | 只显示摘要与深链 | 共享会话、成员互动和可见交接 |
| 谁计算任务状态 | 投影权威领域对象 | 同样只投影，不另建状态真相 |
| 文件在哪里工作 | 链接到所属 Workspace | Group Workspace 承载群组共享过程文件 |
| Review/Approval 在哪里执行 | 展示“待我处理”并跳转原动作 | 展示协作上下文并调用同一原领域动作 |

同一正式任务可以同时出现在工作台和协作群组：工作台回答“我的工作现在怎样、我要做什么”，协作群组回答“参与者如何共同推进”。两者不是互斥执行器，也不各自创建一份任务。

#### 2.4.8 P0 消息转正式任务合同

P0 只支持把**一条**已持久化的 Group 消息显式转换为一个正式 Task。多消息合并、从临时草稿转换、一个来源消息拆成多个
Task 都不是本轮能力。转换规则如下：

| 决策 | P0 合同 |
|---|---|
| 谁可以转换 | 当前 tenant 中仍处于 active 状态、且仍能读取该 Group/session/message 的人类成员 |
| 哪些消息可以转换 | 人类或 Agent 已持久化的可见消息；系统事件、删除/隐藏消息、临时输入和未落库流式片段不可转换 |
| 是否立即创建 | 否。用户点击“转为正式任务”后先看到确认面板；确认前不得创建 Task、Run、Credits 消耗或外部副作用 |
| 谁是主要责任主体 | 至少选择一个当前 Group 内可执行且当前用户可调用的 Agent；有序参与者中的第一位是该 Task 唯一且不可变的 `primary_owner`，其余 Agent 是 `collaborator` |
| 人类成员的角色 | requestor、协作者、reviewer 或 approver；P0 不把人类成员写入 Task executor，也不允许没有 Agent owner 的正式 Group Task |
| 来源与任务基数 | 同一 tenant、Group 和 source message 在 P0 最多对应一个正式 Task；重复点击、并发确认和网络重放返回既有 Task |

确认面板至少展示并让用户确认：来源消息摘要、任务标题、目标与完成标准、Group/session、主要责任 Agent、协作 Agent、能力与
权限检查、可能的审批/费用提示。服务端必须重新读取消息、成员和 Agent 事实；客户端提交的名称、摘要、cursor 或成员标签都不是
权威事实。

#### 2.4.9 关联关系与数据真源

P0 不新增 `GroupTask`、`GroupTaskStatus` 或另一套 Runtime。关联关系沿用现有对象：

- `Task.origin_type = "group"`，`Task.group_id` 指向唯一主要协作 Group；
- immutable `executor_snapshot/work_statement.origin` 保存服务端解析的 `group_id/session_id/message_id/message_cursor/message_excerpt`；
- Agent 参与者顺序和 `primary_owner/collaborator` 责任写入 immutable executor snapshot；
- Group Runtime 继续用 `AgentRun.correlation_id = "work-task:{task_id}"` 关联 root/child runs；
- 原消息保持原样，消息上的任务标识只是 Work 投影，不修改消息正文，也不成为任务状态真源；
- 只有将来确有高频按 source message 做运营查询的证据时，才评估规范化来源列和索引；P0 不做 migration。

#### 2.4.10 读取、动作与双向导航合同

Group 页面在现有侧栏提供“关联任务”，来源消息展示任务标识；两者都进入 `/work/:taskId`。Work 详情提供返回原
Group/session/message 的二级入口，左侧导航不增加新入口。

当前 active Group 成员可以读取协作所必需的安全投影：Task 标题与目标、来源、主要责任主体、协作 Agent、独立状态轴、
Group root/child 运行摘要、最新交接和更新时间。Artifact 内容、Review 详情、Approval 详情、Delivery 内容与具体 action
仍逐对象鉴权；没有原领域权限时必须省略或脱敏，不能因为“是群管理员/群成员”而扩大权限。Task creator、当前 reviewer、
approver 或恢复责任人按各自权威关系获得对应详情和 action。

成员被移除、membership 失效、tenant 切换或对象授权撤销后，服务端读取和 action 立即 fail closed；前端必须清除或隔离旧
query/cache/实时增量。群管理员权限只覆盖 Group 设置与成员管理，不继承任务重试、Artifact、Review、Approval 或 Delivery
权限。

#### 2.4.11 失败、交接与恢复合同

- Group Runtime 的 root run、participant child runs 和 handoff event 是执行真相；页面必须展示当前 actor 与失败参与者。
- 任一必要 participant 失败或取消时，Task 不得显示整体完成；应显示阻塞/失败事实，并把 creator recovery 投影到工作台。
- `delivery_succeeded`、`delivery_failed` 以及渠道投递回执只描述执行结果通知是否到达协作现场，不属于 Run lifecycle，也不能覆盖 `run_completed/run_failed/run_cancelled`。
- P0 retry 由 Task creator 在工作台触发，生成新 attempt；重试前重新校验 Group membership、Agent 可见性、可执行状态、模型路由与当前授权。
- retry 默认复用该 Task 的 immutable participant snapshot；任一原参与者已失效时返回可解释冲突，不静默换人、不静默缩减参与者。
- 重新分配主要责任主体、修改参与者集合或把 Task 转移到另一 Group 必须是未来独立、显式且带审计的动作，不混入 P0 retry。

#### 2.4.12 P0 明确排除项

本轮不改左侧导航，不做 Kanban/Gantt，不支持多 Group 主归属、多消息 bundle、一个消息拆多 Task、人类作为 Task executor、
静默建群/加人/转任务、自动重分配、复制 Workspace、第二套任务状态机或 Group 专属 approve/review API。普通消息、`@Agent`
执行和 Workspace 文件继续只是协作事实，除非用户完成显式确认，否则都不创建正式 Task。

### 2.5 Workspace：工作现场

- Workspace 是执行中的文件、草稿、来源、脚本、中间产物和版本现场。
- Agent Workspace 和 Group Workspace 保留现有所有权；工作台只建立深链和索引。
- Workspace 不是最终交付清单，也不等于公司网盘。

### 2.6 Deliverable：正式产物

- Deliverable 是有工作说明、版本、质量检查、审批、交付状态和 Artifact 的正式结果。
- 产出者在自己的时间线里给出结果；右侧详情承载检查和交付动作；输入框不显示已完成产物。

### 2.7 广场：经验与员工发现

目标广场包含两个明确分区：

- `经验库`：已审核发布、可供人和 Agent 复用的公司经验；
- `员工市场`：发现公司模板、内置角色和可招聘数字员工。

当前 `/plaza` 已把页面标题收敛为团队经验库，并通过发现中心保留 `TalentMarketModal` 员工市场入口。两者共享发现入口但不共享数据模型：发布 Experience 不会创建 Agent，招聘员工也不会自动发布经验。

## 3. 目标任务路径

```text
用户表达意图
  → 工作台/我的助理识别工作类型
  → 补齐必要约束
  → 平台提议责任主体
  → 能力/权限/费用/审批预检
  → 用户确认工作说明
  → 创建稳定 Task/Deliverable 与 Run
  → 在 Agent 或 Group 工作现场执行
  → 产物进入 Workspace 并登记 Artifact
  → 检查、修改、批准与交付
  → 可选择沉淀为个人快捷工作、公司模板或 Experience
```

用户仍可以直接进入某个 Agent chat 或 Group 发起任务；这些是专业入口，不是唯一入口。所有入口最终必须进入同一套持久业务对象。

## 4. 执行者选择规则

| 用户意图 | 默认责任主体 | 说明 |
|---|---|---|
| 备忘、跟进、草拟、个人安排 | 私人助手 | 保持私人上下文 |
| 一次性调研、一次 PPT、一次广告视频 | 临时专家 | 不要求招聘长期员工 |
| 持续运营、每天汇报、长期客户跟进 | 数字员工 | 需要记忆、Trigger、Channel、KPI |

## 5. WorkBuddy 对比所得结论

先前实际观察到的 WorkBuddy 使用路径是任务优先：用户先描述结果，系统再澄清、确认和执行，Skill/Tool/Provider 不占据普通用户的第一步。这支持 Astra 隐藏内部能力结构、增加工作台的方向。

该观察不能被夸大为 WorkBuddy 已证明完整商业交付；先前测试没有形成可独立验收的最终交付物。Astra 的差异化应是把任务优先入口与现有企业 Agent、Group、权限、Credits、Workspace 和可审计交付结合起来，而不是复制一个通用聊天首页。

## 10. 身份与公司入口的目标分流

注册后不再统一落到“创建或加入公司”二选一弹窗，而由服务端事实决定下一步：

```text
完成身份验证
  ├─ 有待处理公司邀请 → 查看并接受/拒绝邀请
  ├─ 有 company.create → 创建公司并成为 org_owner
  ├─ 同时具备两者 → 明确选择加入或创建，不静默消费邀请
  └─ 两者都没有 → 等待邀请/申请加入
```

- 创建公司是账户级权益，不由当前公司的 `member/org_admin` 角色决定；
- 加入公司使用绑定邮箱、目标角色和有效期的 `OrganizationInvitation`；
- 已有账号加入第二家公司只新增 membership，不覆盖当前公司；
- 公司初始化只配置公司事实与安全默认策略，个人 Onboarding 才配置职位、工作时间和私人助手；
- 多公司切换必须换取 membership-scoped token，并清理 tenant query、WebSocket 和浏览器会话；
- 平台运营者无公司 membership 时进入独立平台控制台，不经过公司 Onboarding。
